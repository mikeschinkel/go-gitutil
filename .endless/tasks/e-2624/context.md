Decided by Mike on 2026-11-14 while planning go-goutil's extraction (E-2608, "Q1: C"). gomion's gommod/goutils/commit_signals.go classifies commit messages by the Conventional Commits spec: a `!` before the colon or a `BREAKING CHANGE:`/`BREAKING-CHANGE:` footer is breaking, `feat:` or `feat(scope):` is a feature, `fix:` likewise a fix, and the highest signal across the commits wins (breaking > feat > fix). It took `[]gitutils.CommitLogEntry`, the package's only gitutils import. That parsing knows nothing of Go, and go-gitutil's conventional_commit.go already holds the conventional-commit type table, so the classification belongs here, with the convention pluggable through a closure so a project using another prefix scheme can supply its own. The step that maps a signal to goutil's FindingType (the API-compatibility verdict) stays in gomion, so neither go-goutil nor go-gitutil imports the other.

For Add with Exclude that is harmless; for gomion's module graph a caller may want git's view. Mike asked that filtering be performant: one process for all paths, not one per directory. `git check-ignore --stdin -z` answers for every path on stdin in a single run. go-gitutil has IgnoredFiles (an `ls-files -i` listing of the whole tree) but no check against a given list of paths.
